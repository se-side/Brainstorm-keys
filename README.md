# Brainstorm-keys

**画面を見ずに、音だけで思考するためのキーボード入力アプリ。**

Bluetooth キーボードを iPhone に繋ぎ、画面を伏せたまま／目を閉じたまま打鍵する。
打鍵は心地よい音で返り、書き溜めたテキストはショートカット一発で AI に渡る。
誤字も、かな漢字変換も、要約も AI 側でやる。答えは短く、音声で耳に返ってくる。

> 目を閉じて、耳だけで、頭の中を吐き出し続けるための道具。

---

## 1. コンセプト

ブレインストーミングの最大の敵は「画面を見て、直したくなること」。
このアプリは**視覚フィードバックを意図的に捨てる**ことで、思考の流れを止めない。

| 普通のメモアプリ | Brainstorm-keys |
| --- | --- |
| 打った文字を目で確認する | 打鍵音で「入った」ことだけ確認する |
| 変換候補を選ぶ | ローマ字で打ち捨てる。変換は AI がまとめてやる |
| 誤字が気になって戻る | 戻らない。誤字訂正は AI がまとめてやる |
| 読んで考える | 聴いて考える |

### 中心にある割り切り：IME を使わない

日本語 IME は「変換候補を目で見て選ぶ」ことが前提で、ブラインド入力と根本的に相性が悪い。
そこで **キーボードは英字（IME オフ）のまま、ローマ字をベタ打ちする。**

```
kyou ha atarasii kikaku no hanasi wo kangaeta
```

これを AI が受け取り、かな漢字変換・誤字訂正・句読点補完までまとめて行う。
「変換」という操作そのものを、入力ループの外に追い出す設計。

## 2. 動作環境と、なぜ PWA なのか

開発環境が iPhone 17 のみ、という制約から選択肢は事実上ひとつ。

- **ネイティブ iOS アプリ** → Xcode（= Mac）が必須。除外。
- **PWA（Web アプリ）** → iPhone だけで、書く・配る・使う が完結する。**これを採る。**

| 項目 | 使うもの |
| --- | --- |
| 実行環境 | iOS Safari 18+（ホーム画面に追加してスタンドアロン起動） |
| 端末 | iPhone 17 + Bluetooth 物理キーボード |
| 打鍵検出 | `keydown` / `keyup` イベント |
| 効果音 | Web Audio API（**音源ファイルを一切持たず、その場で合成する**） |
| 読み上げ | Web Speech API `speechSynthesis`（`ja-JP` / Kyoko） |
| AI | Gemini API（`fetch` でブラウザから直接呼ぶ） |
| 配信 | GitHub Pages（`main` に push すれば数十秒で反映） |
| 保存 | `localStorage`（バッファ・履歴・API キー・設定） |

サーバーもビルドもバンドラも無い。`index.html` を開けば動く。
**iPhone で編集 → commit → Safari で再読込、が開発ループのすべて。**

## 3. 使い始める

### 配信する（最初の一度だけ）

1. GitHub の **Settings → Pages** を開く
2. Source を **Deploy from a branch**、ブランチをこのリポジトリの `main` / `(root)` にする
3. 数十秒後、`https://<ユーザー名>.github.io/Brainstorm-keys/` で開けるようになる

ビルド手順は無い。push したものがそのまま動く。

### 端末を用意する

1. 上の URL を Safari で開き、共有ボタンから **ホーム画面に追加**（全画面で起動し、Safari の UI に邪魔されない）
2. **設定** を開き、[Google AI Studio](https://aistudio.google.com/apikey) で取得した **Gemini API キー**を貼る
3. イヤホンを接続し、**消音スイッチを解除**する
4. Bluetooth キーボードを繋ぎ、入力言語を **英字（ABC）** にする（`Ctrl + Space` で切り替わる）

### 使う

画面をタップするか、何かキーを押すと「準備できました」と喋る。ここから先は画面を見ない。
あとはローマ字で打ち続け、区切りたくなったら `Ctrl + Enter` や `Ctrl + S` を押す。

## 4. 音のデザイン

イヤホン装着が前提。**画面の代わりに、音が全ての状態を伝える。**
音は全て Web Audio API で合成する（アセットの管理・ダウンロード待ちが無く、レイテンシが最小になる）。

### 4.1 打鍵音

打鍵音は「入力が通った」という**唯一の確認手段**なので、遅延ゼロ・取りこぼしゼロが絶対条件。

| キー | 音 | 意図 |
| --- | --- | --- |
| 通常キー | 短いクリック。ピッチを ±数% でランダム揺らし | 機械的な連打感を消し、打鍵が「気持ちいい」 |
| スペース | やや低く、丸い音 | 語の区切りが耳で分かる |
| Enter | 上向きの 2 音 | 行を終えた感覚 |
| Backspace | 下向きの短い音 | 消した感覚 |
| 句点 `.` `、` | 微かなアクセント | 文が閉じた感覚 |
| 修飾キー単独 | 無音 | ノイズを増やさない |

連打時は同時発音数を制限し、音が濁らないようにする（ボイススティール）。

### 4.2 状態音（アンビエント）

| 状態 | 音 |
| --- | --- |
| 待機（入力中） | 無音 |
| 送信した | 上向きの短いスワイプ音。「飛んでいった」感 |
| AI 考え中 | **低音量のアンビエントパッド + ゆっくりした脈動**。ずっと鳴っているので、疲れない音量・音色にする |
| 回答が来た | 柔らかいベル。直後に読み上げ開始 |
| エラー | 低い 2 連音。詳細も音声で短く言う |
| バッファ消去 | 下向きのスワイプ音 |

「考え中」の音が**鳴り止まないこと自体が「まだ待っている」の合図**になる。画面を見る必要がない。

### 4.3 読み上げ

- 声は `ja-JP`、速度はやや速め（既定 1.15）。設定で変更可能。
- **AI には「短く、口語で、箇条書きにしない」とシステム指示する。** 耳で聴くのに箇条書きは向かない。
- 読み上げ中も打鍵は受け付ける。次の考えを止めない。
- 打鍵を始めたら読み上げは自動で止める（`Ctrl+.` でも停止）。

## 5. ショートカット

修飾キーは **Ctrl** に統一する（Cmd 系は Safari 自身に奪われる組み合わせが多いため）。
どのショートカットも、**実行した瞬間に固有の音**で「何が起きたか」を返す。

| キー | 動作 | 耳に返るもの |
| --- | --- | --- |
| `Ctrl + Enter` | **これまでの全文をプロンプトとして AI に送る** | 送信音 → 考え中 → 回答を音声で |
| `Ctrl + S` | 全文を**要約**させる | 同上 |
| `Ctrl + F` | 誤字訂正 + かな漢字変換して**バッファを清書で置き換える** | 完了音 + 「整えました」 |
| `Ctrl + Q` | 直前の一文だけを AI に投げる（軽い質問用） | 同上 |
| `Ctrl + R` | 直前の回答をもう一度読み上げ | 読み上げ |
| `Ctrl + L` | 今書いている**末尾の一文**を読み上げ（「どこまで書いたか」の確認） | 読み上げ |
| `Ctrl + .` | 読み上げ・考え中音を停止 | 停止音 |
| `Ctrl + K` | バッファを消去（**2 回連続押しで確定**。誤爆防止） | 1 回目は確認音、2 回目で消去音 |
| `Ctrl + Z` | 直前の消去・清書を取り消す | 復帰音 |
| `Ctrl + /` | ショートカット一覧を音声で読み上げ | 読み上げ |

`Ctrl+Enter` と `Ctrl+S` の違い：前者は「**これについて考えてくれ**」（対話）、後者は「**これをまとめてくれ**」（要約）。
どちらも、書き溜めたテキストそのものがプロンプトになる。

## 6. AI（Gemini）の使い方

- モデル：`gemini-2.5-flash`（耳で待てる速さを最優先。応答が遅いモデルはこの体験を壊す）
- 呼び出し：ブラウザから `fetch` で REST を直接叩く。SDK もサーバーも挟まない。
- **ストリーミング（SSE）で受け取り、文が閉じた時点から順に読み上げ始める**。全部待つと体感が重い。
- 出力は必ず短文・口語。長い回答は「まず結論だけ」を先に返させる。

### 用途ごとのプロンプト

| ショートカット | AI にやらせること |
| --- | --- |
| `Ctrl+F` 清書 | ローマ字 → 日本語。誤字訂正・句読点補完。**内容は足さない・要約しない** |
| `Ctrl+S` 要約 | 論点を 2〜3 個。各 1 文。話し言葉で |
| `Ctrl+Enter` 対話 | 全文を読んだ上で、短く応答。深掘りの問いを 1 つ返す |

### API キーの扱い（重要）

- キーは端末の `localStorage` にのみ保存する。リポジトリには**絶対に**コミットしない。
- **ブラウザから直接叩く以上、キーは端末上で読める。**個人利用専用と割り切る。
- Google AI Studio でキーに**リファラ制限**（GitHub Pages のドメイン）と**利用上限**を設定しておくこと。
- 打った内容は Gemini API に送信される。機微な内容は打たない。

## 7. iOS 特有の落とし穴（実装で織り込み済み）

| 問題 | 対策 |
| --- | --- |
| 音声はユーザー操作なしに鳴らせない | **画面のタップ、または最初の打鍵**で `AudioContext` と `speechSynthesis` を解錠する。解錠できたら「準備できました」と喋るので、それが確認になる |
| **消音スイッチで Web Audio が消える** | 無音の `<audio>` を `playsinline` で再生してオーディオセッションを playback に寄せる。それでも駄目なら「消音を解除してください」と設定画面に明記する |
| 放置で画面ロック → アプリが止まる | Screen Wake Lock API でロックを抑止（iOS 16.4+）。失効時は再取得する |
| 一部の `Ctrl` 併用キーを Safari が奪う | `preventDefault()` で握る。それでも奪われる場合は `localStorage` の `bk.keymap.v1` に `{"j":"ask"}` のような上書きを置いて差し替える（設定 UI は Phase 4） |
| Safari のインスペクタが（Mac 無しでは）使えない | 画面下に**オンスクリーン・ログ**を常時表示。加えて致命的エラーは音声で読み上げる |
| バックグラウンドで JS が止まる | 復帰時に音声を解錠し直し、画面ロック抑止を取り直す。バッファは打鍵ごとに `localStorage` へ保存するので、落ちても失わない |

## 8. 構成

```
index.html                 画面（状態表示・オンスクリーンログ・設定パネル）
manifest.webmanifest       ホーム画面に追加するための定義
sw.js                      Service Worker（network-first。オフラインでも起動する）
icons/                     アイコン（180 / 192 / 512）
src/
  main.js                  全体の配線と状態遷移
  audio.js                 打鍵音・状態音・環境音の合成（Web Audio）
  keys.js                  キー入力とショートカットの解釈
  buffer.js                テキストバッファ、Undo、localStorage 永続化
  gemini.js                Gemini API 呼び出し（SSE ストリーミング）
  speech.js                読み上げと、文単位の逐次読み上げ
  prompts.js               モードごとのシステム指示
  log.js                   オンスクリーンログ
```

ビルド無し・依存無しの ES Modules。**1 ファイルが短く、iPhone の画面でも編集できる**ことを優先する。

## 9. iPhone だけでの開発フロー

1. **編集**：GitHub モバイル or `github.dev`（Safari で GitHub の `.` キー相当）でファイルを直接編集して commit
   - 本格的にやるなら **Working Copy**（iOS の Git クライアント）+ 好みのエディタ
2. **確認**：`main` に push → GitHub Pages が更新 → Safari で開いて再読込
3. **常用**：Safari の「ホーム画面に追加」でスタンドアロン起動。Bluetooth キーボードを繋いで使う
4. **デバッグ**：オンスクリーンログ + 音声エラー通知（インスペクタの代わり）

Service Worker のキャッシュで古い版が出ることがあるので、開発中はバージョン文字列を上げて確実に更新する。

## 10. ロードマップ

- **Phase 1 — 打てて、鳴る**（実装済み）
  キー入力の取得、打鍵音の合成、バッファの永続化、オンスクリーンログ。
- **Phase 2 — 送れて、返る**（実装済み）
  Gemini の SSE 接続、全ショートカット、送信音・考え中の環境音・文単位の逐次読み上げ。
- **Phase 3 — 手放せる**（実装済み）
  PWA 化（ホーム画面・オフライン起動）、Wake Lock、消音スイッチ対策、読み上げ速度と音量の設定。
- **Phase 4 — 磨く**（これから。実機で聴きながら詰める）
  音色とタイミングの調整、ショートカット再割り当ての UI、履歴のセッション管理と書き出し。

### 実機で最初に確かめること

ヘッドレスブラウザでは、ロジック（入力・SSE の解析・状態遷移・オフライン起動）までしか確認できない。
**音の良し悪しと iOS 固有の挙動は実機でしか分からない。** 触ったら、まずこの順で見てほしい。

1. 打鍵音が気持ちいいか。速く打ったときに遅れたり濁ったりしないか
2. 消音スイッチを入れたままでも鳴るか（鳴らなければ解除して使う）
3. 「考え中」の環境音が、長く聴いても疲れない音量・音色か
4. `Ctrl` 併用のショートカットが Safari に奪われていないか
5. 読み上げ速度 1.15 倍が速すぎ・遅すぎでないか

## 11. 未決事項

- 考え中のアンビエント音の**性格**（静かなパッド／低い持続音／ごく微かなノイズ）。実際に長時間聴いて決めたい。
- 打鍵音を**キーごとに変える**か（例：母音でピッチを変える）。情報量は増えるが、うるさくなるリスクがある。
- 履歴の**セッション区切り**の扱い（時間で切る／`Ctrl+K` で切る）。
- 英語まじりの入力をどう扱うか（ローマ字なのか英単語なのかの判別を AI に任せる範囲）。
